# Лабораторная работа 2 — `avlset`

В этом каталоге находится шаблон программы на C и набор тестов для самостоятельной проверки. Условие, уровни сложности и ограничения приведены в PDF на сайте курса.

## 1. Окружение

Программа должна собираться и работать в Linux. На **Windows используйте WSL с Ubuntu** (инструкция по установке WSL есть на сайте курса). Команды ниже выполняются **в терминале Ubuntu**, а не в PowerShell. Исходный код можно редактировать в VS Code через расширение WSL.

На Ubuntu / WSL установите необходимые инструменты:

```bash
sudo apt update
sudo apt install build-essential python3
```

На macOS нужны компилятор C, `make` и Python 3.9 или новее. Для режима с санитайзерами необходим компилятор с поддержкой AddressSanitizer и UndefinedBehaviorSanitizer; предоставленный `Makefile` использует `gcc`. Если в вашей конфигурации macOS `make sanitize` не работает, проверяйте этот режим в Linux / WSL.

Проверка наличия инструментов:

```bash
gcc --version
make --version
python3 --version
```

## 2. Структура проекта

```text
lab-02/
├── Makefile
├── include/
│   └── avlset.h
├── src/
│   ├── main.c
│   └── avlset.c
├── run_tests.py
├── generate_tests.py
├── TESTS_README.md
└── tests/
    ├── L4_*.in
    ├── L4_*.expected
    └── ...
```

- `include/avlset.h` — обязательный публичный интерфейс. Не изменяйте его.
- `src/main.c` — готовый обработчик команд. Не изменяйте его.
- `src/avlset.c` — место для вашей реализации. Изначально содержит заглушки.
- `Makefile` — единые команды сборки.
- `tests/` — входные данные (`.in`) и соответствующие ожидаемые ответы (`.expected`).
- `run_tests.py` — запуск тестов, сравнение ответов, измерение времени и диагностика ошибок.
- `generate_tests.py` — детерминированное пересоздание предоставленных тестов; **для обычной проверки запускать не требуется**.

Тип `AvlSet` объявлен в заголовке как неполный. Полное определение `struct AvlSet`, типы узлов и вспомогательные функции должны оставаться внутри `.c`-файлов. Структуры данных и алгоритмы необходимо написать самостоятельно. Не изменяйте сигнатуры функций в `avlset.h`.

Если добавляете собственные `.c`-файлы, включите их в переменную `SOURCES` в `Makefile`. Проверяющий сможет вызывать функции из `avlset.h` независимо от `main.c`.

## 3. Сборка и запуск

Все команды выполняйте **из корня проекта**, где находится `Makefile`.

| Команда | Назначение |
| --- | --- |
| `make` | Обычная сборка с оптимизацией `-O2` |
| `make debug` | Сборка без оптимизации (`-O0`) и с отладочной информацией (`-g3`) |
| `make sanitize` | Сборка с AddressSanitizer и UndefinedBehaviorSanitizer |
| `make clean` | Удаление исполняемого файла |

Исполняемый файл называется `avlset` и создаётся в корне проекта.

Пример ручного запуска на входном файле:

```bash
make
./avlset < tests/L4_basic.in
```

Замените `L4_basic.in` на **существующее** имя файла из каталога `tests/` (список можно посмотреть командой `ls tests/*.in`). Можно также запустить `./avlset` без перенаправления и вводить команды вручную; завершение ввода — `Ctrl+D`.

После изменения режима сборки запускайте соответствующую команду заново. Тестовый скрипт при обычном запуске пересобирает программу автоматически.

## 4. Автоматические E2E-тесты

Требуется Python **3.9+**. Сторонние Python-пакеты не нужны.

Базовая проверка выбранного уровня:

```bash
python3 run_tests.py --level 4
python3 run_tests.py --level 6
python3 run_tests.py --level 8
python3 run_tests.py --level 9
python3 run_tests.py --level 10
```

Уровень должен быть одним из `4`, `6`, `8`, `9`, `10`. При выборе уровня выполняются тесты **этого и всех предыдущих уровней**.

Добавить стресс-тесты:

```bash
python3 run_tests.py --level 8 --stress
python3 run_tests.py --level 10 --stress
```

Запустить тесты с санитайзерами:

```bash
python3 run_tests.py --level 8 --sanitize
python3 run_tests.py --level 10 --sanitize --stress
```

**Внимание:** `--sanitize` сам вызывает `make -B sanitize`; предварительно запускать `make sanitize` не требуется. Аналогично, без этого флага скрипт вызывает `make -B all`. После санитайзерной проверки обычный запуск скрипта снова соберёт обычную версию программы.

Скрипт для каждого теста выводит `[ OK ]`, `[FAIL]` или `[TIME]`, время выполнения и, при ошибке, её причину. При неправильном ответе указывает первую несовпадающую строку, ожидаемое и фактическое значения. При аварийном завершении печатает начало сообщения об ошибке.

Пример диагностики:

```text
[FAIL] L8_example (0.012 с): строка ответа 5: expected='3', actual='4'
[TIME] L8_stress_example: превышен лимит 12 с
```

Это иллюстрация формата сообщений, а не названия обязательных тестов.

По умолчанию лимит составляет **3 секунды на обычный тест** и **12 секунд на стресс-тест**. В режиме `--sanitize` оба лимита увеличиваются втрое. Это **ориентиры для самопроверки**, а не официальные лимиты преподавательского стенда. Для более медленного компьютера можно задать свои значения:

```bash
python3 run_tests.py --level 10 --stress --timeout 5 --stress-timeout 30
```

Для запуска уже собранного файла без повторной компиляции:

```bash
python3 run_tests.py --level 8 --no-build
```

При этом скрипт **не проверяет**, с какими флагами был собран существующий исполняемый файл. Не используйте `--no-build` для проверки санитайзеров, если предварительно не выполнили `make sanitize`.

## 5. Как разобраться с ошибкой

Если тест не прошёл, найдите его входной файл в `tests/` и запустите программу отдельно:

```bash
make debug
./avlset < tests/ИМЯ_ТЕСТА.in
```

Для сравнения с ожидаемым ответом:

```bash
./avlset < tests/ИМЯ_ТЕСТА.in > actual.txt
diff -u tests/ИМЯ_ТЕСТА.expected actual.txt
```

Здесь `ИМЯ_ТЕСТА` — имя, которое вывел тестовый скрипт (без расширения). Файл `actual.txt` создаётся только для локальной диагностики.

При ошибках памяти соберите программу с санитайзерами и повторите проблемный тест:

```bash
make sanitize
./avlset < tests/ИМЯ_ТЕСТА.in
```

Санитайзеры могут выявлять выход за границы памяти, использование освобождённой памяти, некоторые случаи неопределённого поведения и утечки памяти (поддержка проверки утечек зависит от платформы).

## 6. Что проверяется

Тесты проверяют ответы программы на последовательности команд. Они **не доказывают** требуемую асимптотическую сложность, корректность внутренней архитектуры и отсутствие всех ошибок памяти. В частности, прохождение тестов на `DELETE_RANGE` не заменяет требование реализовать алгоритм, указанный в условии.

Преподаватель может использовать дополнительные закрытые тесты и напрямую вызывать функции публичного интерфейса. На защите нужно объяснить структуру данных, инварианты, управление памятью и сложность реализованных операций.

Перед сдачей проверьте, что проект собирается в Linux / WSL после `make clean`, что все необходимые исходные файлы находятся в вашем репозитории и что работа не зависит от файлов, оставшихся только на вашем компьютере.
