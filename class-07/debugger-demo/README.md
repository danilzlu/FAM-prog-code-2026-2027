# Демонстрация отладчика C в VS Code

Небольшая программа с **намеренной логической ошибкой** в бинарном поиске. Она компилируется без предупреждений, но зависает при поиске числа `23`. Задача — обнаружить причину **отладчиком**, а не сразу читать готовое исправление.

## Состав папки

- `main.c` — демонстрационная программа с ошибкой;
- `.vscode/launch.json` — конфигурации отладки для macOS, Linux и Windows;
- `.gitignore` — исключение собранных программ и служебных файлов.

Откройте **именно папку `debugger-demo`** через **File → Open Folder** в VS Code. Пути `${workspaceFolder}/program` и `${workspaceFolder}/program.exe` отсчитываются от открытой папки. Если открываете корень общего репозитория, вместо этого измените пути в `launch.json` или откройте подпапку отдельно.

## Подготовка и запуск

Установите VS Code и компилятор C. Для Linux и Windows (GDB/MSVC) требуется расширение **C/C++** от Microsoft (`ms-vscode.cpptools`); для macOS в предлагаемой конфигурации — **CodeLLDB** (`vadimcn.vscode-lldb`).

### macOS (Clang + LLDB)

1. Установите Command Line Tools: `xcode-select --install` (если ещё не установлены).
2. Установите расширение **CodeLLDB** в VS Code.
3. В терминале VS Code выполните:

   ```bash
   clang -std=c17 -Wall -Wextra -g -O0 main.c -o program
   ```

4. В панели **Run and Debug** выберите **macOS — LLDB (CodeLLDB)** и нажмите `F5`.

**Почему не исходная конфигурация с `MIMode: "gdb"`?** На macOS `/usr/bin/gdb` обычно отсутствует: штатный отладчик Xcode — LLDB. Расширение CodeLLDB использует `type: "lldb"`, а не `cppdbg` с `MIMode: "gdb"`.

### Linux (GCC + GDB)

1. Установите GCC и GDB (пример для Debian/Ubuntu: `sudo apt install build-essential gdb`).
2. Установите расширение **C/C++** от Microsoft.
3. Соберите программу:

   ```bash
   gcc -std=c17 -Wall -Wextra -g -O0 main.c -o program
   ```

4. Выберите **Linux — GDB**, нажмите `F5`. Если GDB находится не в `/usr/bin/gdb`, измените `miDebuggerPath`.

### Windows (вариант A: MSYS2 UCRT64 + GCC/GDB)

1. Установите MSYS2. В терминале **MSYS2 UCRT64** установите компилятор и отладчик:

   ```bash
   pacman -S --needed mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-gdb
   ```

2. Установите расширение **C/C++** от Microsoft.
3. Убедитесь, что `C:\msys64\ucrt64\bin` добавлен в `PATH` терминала VS Code, либо используйте полный путь к `gcc.exe`:

   ```powershell
   C:\msys64\ucrt64\bin\gcc.exe -std=c17 -Wall -Wextra -g -O0 main.c -o program.exe
   ```

4. Выберите **Windows — MinGW-w64 GDB** и нажмите `F5`. При иной установке MSYS2 измените `miDebuggerPath` в `.vscode/launch.json`.

### Windows (вариант B: MSVC)

1. Установите Visual Studio Build Tools с компонентами **Desktop development with C++**.
2. Откройте **Developer PowerShell for VS** (или Developer Command Prompt), перейдите в папку примера и выполните:

   ```powershell
   cl /nologo /W4 /Zi /Od /Fe:program.exe main.c
   ```

3. Установите расширение **C/C++** от Microsoft, откройте папку в VS Code, выберите **Windows — MSVC debugger**, нажмите `F5`.

MSVC и MinGW — **альтернативные** варианты, устанавливать оба не требуется. В случае MSVC отладка должна запускаться в окружении, где доступны необходимые компоненты Visual Studio.

## Сценарий демонстрации (15–20 минут)

| Шаг | Действие преподавателя | Что наблюдаем |
|---|---|---|
| 1 | Собрать с `-g -O0` и запустить без отладчика | Выводится первая строка, затем программа зависает |
| 2 | Остановить программу (`Ctrl+C` в терминале) | Ошибка не связана с компиляцией |
| 3 | Поставить breakpoint на строке `while (left < right)` | Выполнение остановится внутри функции |
| 4 | Нажимать `F10` (**Step Over**) | Меняются `left`, `right`, `mid` |
| 5 | Добавить в **Watch** выражения `left`, `right`, `mid`, `a[mid]`, `target` | При `left = 4`, `right = 5` вычисляется `mid = 4` снова и снова |
| 6 | Открыть **Call Stack** | Видно вызовы `main → binary_search` |
| 7 | Показать `F11` (**Step Into**) при новом запуске | Переход из `main` в `binary_search` |
| 8 | Исправить одну строку, пересобрать, снова запустить `F5` | Программа завершается и выводит `Индекс: 5` |

Кнопки: `F5` — начать/продолжить; `F9` — breakpoint; `F10` — шаг с обходом вызова; `F11` — шаг с заходом; `Shift+F11` — выйти из функции; `Shift+F5` — остановить. На некоторых ноутбуках нужно удерживать `Fn`.

### Вопросы аудитории

1. Почему компилятор не предупреждает об этой ошибке?
2. Какой инвариант должны сохранять `left` и `right`?
3. Что гарантирует завершение цикла бинарного поиска?
4. Почему ошибка проявляется не при каждом искомом значении?
5. Что изменится, если поискать число `2`?

### Подсказка преподавателю (спойлер)

В ветке `a[mid] < target` используется `left = mid`, хотя `mid` уже проверен и не равен `target`. Для полуинтервала `[left, right)` следует использовать `left = mid + 1`. В противном случае при `right = left + 1` получаем `mid = left`, и граница перестаёт изменяться.

## Важные замечания

- После изменения `main.c` **пересоберите** исполняемый файл: `F5` в этой конфигурации запускает уже собранную программу, а не компилирует исходник автоматически.
- `-g` (или `/Zi`) добавляет отладочную информацию; `-O0` (или `/Od`) отключает оптимизации, чтобы проще сопоставлять исходный код и исполнение.
- Если программа зависла, используйте **Pause** в панели отладки или остановите отладку; не обязательно ждать её завершения.
- Демонстрационная ошибка — логическая, а не ошибка памяти. AddressSanitizer её не обнаружит.
